## 3. 交換の直し（❌1・アプリ側）

- **前**: 「交換する」を押すと端末の中だけでポイントを減らして引換券を出していた（サーバーに記録なし）。電波を切って交換→ログアウト→ログインで残高が戻った。
- **新**: 「交換する」→ サーバーへ1つのトランザクションで「points の減算＋交換の記録」を書く → **届いたのを確かめてから** 4けたのコードと残り時間を出す。お店の流れ（画面を店員が見る・10分）は同じ。
  - 電波が無い／通信に失敗 → 「交換できませんでした。電波の良い所でもう一度お試しください。（交換はしていません。ポイントはそのままです）」と出して交換しない。
  - 残高はサーバーの値で確かめる（端末の数字を書き換えても、サーバーの残高が足りなければ断る）。
  - 「届いたか分からない」（送った直後に電波が切れた等）→ 引換券は出さず、送ろうとした中身を端末に控える。次に「つかう」を開いたとき・起動時にサーバーへ聞き、届いていれば引換券を出す（ポイントだけ減って引換券が出ない、を防ぐ）。届いていなければ 10 分で控えを捨てる。
  - 交換の履歴「お店で交換 …（コード）」は今までどおり端末とサーバーの両方に残る。
- あわせて: 新規アカウントの最初の保存がルールに拒否されたとき（端末に前の人・消されたアカウントの状態が残っている場合）、端末の状態を空にして作り直す（直す前のアプリは読み込み画面で止まる。下の 5.）。
- `admin.html`: 学校対抗の締めで「その月に、学校に入ってからの来店が1回以上」を、本人が自由に書ける teamVisits／teamVisitDay ではなく、ルールで守られている来店日の一覧 visits から数えるようにした（2行）。

## 5. 古い版のアプリへの影響（iOS 1.0.18 以前／Android 1.0.12 以前・今の Web 版）

**ふだんの操作は全部そのまま通る**（上の試験: 直す前の auth.js × 新ルールで 46/46・16/16、ルールの試験の正しい操作 36/36）。古い版の書き込みの形に合わせてある（投稿ポイントはインスタOKに関係なく 20 まで＝ 11/14 より前の版の 20P も通る・紹介の受取は溜まった分を1回で 10 人まで・交換は減らすだけの書き込みも通る）。

古い版で変わること・残ること:
1. 🟥 **交換の穴（❌1）は、古い版では残る。** 古い版は端末の中だけで引換券を出すので、ルールでは止められない（古い版の「減らすだけ」の書き込みを拒否すると、引換券は出るのに残高が減らなくなり逆効果）。ふさがるのは、Web 版は新しい index.html／auth.js を出した時点、ストア版は次の版（iOS 1.0.19／Android 1.0.13）に更新した人から。
2. 会員データが無いのに端末に古い状態が残っている人（運営が会員データを消した・別の人の状態が残った端末で新規登録）は、最初の保存が拒否されて読み込み画面「サーバーに接続できませんでした」で止まる。読み込み画面の「ログアウト」→ログインし直しで直る。前は 1000P まで勝手に戻っていた（これ自体が穴）。新しいアプリは自動で空から作り直す。該当はごく少ないはず（推測）。
3. キャンペーンの受取が、終了日の翌々日以降にサーバーへ届いた場合（終了日に受け取って2日以上電波なし）は拒否される。その日の保存が止まり、翌日の起動でサーバーの状態に戻る（今までの「保存できなかった日」と同じ動き）。
4. 紹介の受取を 10 人分まとめて送り、同じ保存にキャンペーンの受取なども入っていると、ルールの読み取り回数の上限（1回の書き込みで 10 件）で弾かれる。紹介は 10/31 で終わっていて、溜めている人がいても起動 5 秒後に単独で送るので、まず起きない。
5. 来店ポイントは1件 10 まで・ランクアップは段ごとの額まで・ガチャは 100 まで。今の config.js の数字と同じなので影響なし。🟥 config.js の ranks（minVisits・bonus・visitPoints）・referral.points・board.points・ガチャの最大を**上げる**ときは、ルールも同じ日に直す（上げたのにルールがそのままだと、その保存が拒否される）。

## 6. 出す手順

順番が大事: **ルール → Web 版のアプリ → ストア版**。ルールより先にアプリを出すと、交換が全部「交換できませんでした」になる（試験 R9）。

### (1) ルールの deploy（masa の「出して」のあとで）
1. Mac で今の本番を控える: `cd ~/kakiapp_rules && cp firestore.rules firestore_backup_20261116_live.rules`
2. 新ルールを置く: `docs/firestore_rules_fix_20261116.rules` を `~/kakiapp_rules/firestore.rules` にコピー（リポジトリの `firestore.rules` も同じ中身に）
3. `cd ~/kakiapp_rules && firebase deploy --only firestore:rules`（構文エラーがあればここで止まる。エミュレータでは差し替えなしの全文を読み込めている）
4. 出す時間は**営業時間の外か客の少ない時間**に（万一のとき来店の保存に響くため）。出したあと最初の営業時間に下の確かめをする。

### (2) 確かめ方（ルールを出した直後）
- 自分のアカウント（今のストア版のアプリでよい）で: 起動→ログインボーナス、ルーレット、（店で）チェックイン→ガチャ、みんなの一杯の投稿。アプリを閉じて開き直し、ポイントが残っていること。「ポイントの保存ができませんでした」の知らせが出ないこと。
- （開発モードが使える端末なら）エラー表示に `permission-denied` が出ていないこと。
- 翌朝の日報（`scripts/kakiapp_daily.mjs`）で、来店数・ポイントの増え方がいつも通りか。来店があるのに保存が 0 なら拒否を疑って戻す。
- 穴がふさがったかを本番で確かめたいとき（任意・その日まだ来店チェックインしていないアカウントで）: PC のブラウザで試験用アカウントの Web 版を開き、コンソールで `kakiSetState({...kakiGetState(), gachaDate: kakiToday(), points: kakiGetState().points + 100}); cloudPush()` → 「ポイントの保存ができませんでした」が出れば弾かれている。終わったらログアウト（端末の状態が消えて元に戻る）。弾かれるだけで本番のデータは変わらない。

### (3) アプリを出す（ルールの確かめが済んでから）
- Web 版: worktree の commit を main に入れて push（GitHub Pages）。出したら自分で 50P のトッピングを交換し、引換券が出ること・Firebase コンソールの `kakiapp_redeems` に1件できていること・機内モードでは「交換できませんでした」が出ることを確かめる。
- ストア版: 次の版（iOS 1.0.19／Android 1.0.13）に同じ index.html／auth.js を入れて審査へ。古い版の交換の穴はここで更新した人からふさがる。

### (4) 戻し方
- **アプリをまだ出していないとき**: `cd ~/kakiapp_rules && cp firestore_backup_20261116_live.rules firestore.rules && firebase deploy --only firestore:rules`（1〜2分で反映）。
- **新しいアプリを出したあと**: 旧ルールそのままに戻すと交換ができなくなるので、`docs/rules_test_20261116/firestore_rollback_keep_redeems_20261116.rules`（旧ルール＋交換の記録の置き場だけ）を出す。古いアプリも新しいアプリも全部通ることを試験済み（正しい操作 36/36・交換 2/2・保存 46/46・学校 16/16）。穴 ❌2〜6 は元に戻る。

## 7. ルールだけでは無理だったもの（案だけ）

- **⚠7 位置の偽装**: 位置は端末の申告で、ルールからは見えない。入れたのは来店ポイントの上限 20→10 だけ。案: (a) 店内QRを「毎日変わる値」にする（レジ横の画面に出す・運営だけが知る値の日替わりをルールで照合）。(b) 今ある「運営の印」「抜き打ち」（kakiapp_qr/config の spotMax）の割合を上げる＝ルールもアプリも変えずに今日からできる。(c) 未同期の過去日1件の追加（1回の来店で来店数 +2 にできる）をやめる＝古い版の「2日分まとめて保存」が通らなくなるので、古い版が減ってから。
- **⚠8 アカウント作り直しでキャンペーンをもう一度**: ルールだけでは「同じ人」を見分けられない（古い版は受取の記録を別に書かないので、電話番号で1回に絞る照合を入れると古い版の受取が全部止まる）。案: (a) キャンペーンには毎回 `minVisits`（来店◯回以上）を付ける＝今日から運用でできる・ルールでも照合するようにした。(b) 次の版のアプリで「キャンペーンID＋電話番号」の受取記録を同じ書き込みで作り、古い版が減ったらルールで必須にする。今は受取中のキャンペーンが無いので急がない。
- **投稿を消したときにポイントを戻す（e9b1717）は端末側の処理**のまま（改造すれば戻さずに済む・1日 20P まで・来店した日だけ）。ルールで「投稿の削除と減算を同じ書き込みで」にすると古い版の削除が止まるので入れていない。
- **交換の記録を店・運営が見る画面**（今日の引換券一覧）は作っていない。記録は `kakiapp_redeems`（uid・pts・name・code・at）に残るので、admin.html に一覧を足せる。
- 過去の被害の洗い出し（作成直後にポイントが大きい会員・来店ゼロで成立した紹介など）は本番データを読む作業なので、やっていない。
